# Data Model

Everything the vault stores lives in two D1 tables and one JSON document per
item. There is no client side database, no encrypted column and no index
beyond the one on `updated_at`. This document covers the tables, the item
contract, the caps and the identifiers. Read it before changing a column, a
field name or a limit.

## 1. D1 tables

The schema is one migration file, `migrations/0001_init.sql`, applied with
`npx wrangler d1 migrations apply personal-vault --remote` in production and
with `--local` for the local database.

### `items`

| Column | Type | Null | Constraint | Meaning |
|---|---|---|---|---|
| `id` | TEXT | no | PRIMARY KEY | the item id, generated by the client |
| `payload` | TEXT | no | none | the complete item JSON, exactly as the client models it |
| `updated_at` | TEXT | no | none | ISO-8601 timestamp, mirrors `payload.updated_at` |

`idx_items_updated_at` is an index on `items (updated_at DESC)`. It serves the
read order of `GET /api/items`.

There is no `created_at` column, no `revision`, no `deleted_at`, no
`device_id` and no `vault_id`. Creation time lives inside the payload, and
that is the only place it exists.

### `sessions`

| Column | Type | Null | Constraint | Meaning |
|---|---|---|---|---|
| `token` | TEXT | no | PRIMARY KEY | 32 random bytes, hex encoded |
| `created_at` | TEXT | no | none | ISO-8601 timestamp of the login |
| `expires_at` | TEXT | no | none | ISO-8601 timestamp, login time plus 90 days |

Expired rows are removed by `purgeExpiredSessions`, which runs on every
session creation. The table therefore holds the sessions of the last 90 days
at most, plus whatever expired rows exist until the next login.

## 2. Write semantics

A write is an upsert. `PUT /api/items/:id` inserts the row, or replaces
`payload` and `updated_at` when the id already exists. A delete is a hard
delete. There is no soft delete, no tombstone and no undo.

The write is last write wins. Two devices editing the same item both send a
complete item, and the second request replaces the first. The server does not
compare timestamps, does not keep a history and does not signal a conflict.
The client mitigates this by refetching after every mutation and on window
focus, so the visible state converges on the last write.

The `id` in the payload must equal the id in the URL. A mismatch is rejected
with `400 id_mismatch`, because the UI keys on the item id and a mismatch
would fork one record into two rows.

## 3. The item contract

`src/lib/schemas.ts` is the source of truth. It defines a zod
`discriminatedUnion` on `type` with four members.

Base fields, present on every item:

| Field | Type | Rule |
|---|---|---|
| `type` | string | one of `link`, `note`, `snippet`, `credential` |
| `title` | string | required, the form rejects an empty title |
| `tags` | string array | optional, defaults to empty |
| `is_favorite` | boolean | required |
| `is_archived` | boolean | required |
| `created_at` | string | non-empty, ISO-8601 in practice |
| `updated_at` | string | non-empty, ISO-8601 in practice |
| `schema_version` | integer | at least 1, currently always 1 |

The base schema is `.passthrough()`, so unknown fields survive a round trip
through the client. A field that a future version adds stays in the payload
until the client understands it.

Per type fields:

| `type` | Extra fields |
|---|---|
| `link` | `url` (required, non-empty), `description` (optional), `notes` (optional) |
| `note` | `body` (required) |
| `snippet` | `content` (required), `language` (optional, the form defaults it to `text`) |
| `credential` | `website` (optional), `username` (optional), `password` (optional), `notes` (optional) |

`src/lib/types.ts` only re-exports these types. It defines no shapes of its
own, so the contract cannot drift between the two files.

A link URL must use `http:` or `https:`. The rule lives in
`src/lib/validators.ts` and is checked both in the form and again before the
write.

## 4. Tag rules

The rules come from `tagsSchema` in `src/lib/schemas.ts` and the helpers in
`src/lib/validators.ts`. They must agree.

| Rule | Limit |
|---|---|
| Tags per item | 20 |
| Tag length | 64 characters |
| Empty tag | rejected |
| Control characters | rejected, the range `[\x00-\x1f\x7f]` |
| Double quote | rejected, it would break the search query syntax |
| Duplicates in one item | rejected, checked in the UI layer |

A tag may contain spaces and non-ASCII characters. The name is stored as
written, so `Work` and `work` are two different tags.

## 5. Size caps

| Cap | Value | Defined in |
|---|---|---|
| Serialized item | 256 KiB (`PLAINTEXT_ITEM_CAP_BYTES`) | `src/lib/limits.ts` |
| Tags per item | 20 (`TAG_MAX_PER_ITEM`) | `src/lib/limits.ts` |
| Tag length | 64 (`TAG_MAX_LENGTH`) | `src/lib/limits.ts` |

`assertPlaintextSize` in `src/lib/schemas.ts` measures the serialized JSON in
UTF-8 bytes and throws `PlaintextTooLargeError` above the cap. The measurement
itself lives in `src/lib/bytes.ts`, so the schema guard, the UI validator and
the Worker agree on what 256 KiB means. The cap is counted in bytes, not
characters, so multi-byte text costs more than its character count suggests.

The server has its own, larger cap of 300 KiB on the raw request body, so a
client that skips the client side check still cannot push an unbounded
payload.

`src/lib/validators.ts` re-exports the three constants so the UI and the
contract read from one place. Change a value in `src/lib/limits.ts`, not in
`src/lib/validators.ts`.

## 6. Identifiers

Item ids are UUIDv4, generated in the browser by `newRecordId()` in
`src/lib/ids.ts`, which calls `crypto.randomUUID()`. The client generates the
id before the first write, so the primary key is chosen by the client and the
server never mints an item id.

`crypto.randomUUID` only exists in a secure context, so `newRecordId` falls
back to a timestamp and random suffix when it is unavailable. That keeps the
vault usable on a plain-http LAN address instead of throwing in the middle of
a save. The fallback ids are not UUIDv4.

Session tokens are 32 random bytes from `crypto.getRandomValues`, hex encoded
into 64 characters, generated by `newToken()` in `functions/_shared/auth.ts`.

The `items.id` column in `migrations/0001_init.sql` is commented as
"UUIDv4, client-generated", which matches the code.

## 7. Timestamps

`created_at` is set when the item is first created and never changes.
`updated_at` is refreshed on every write, and the same value is written to
the `items.updated_at` column. The client sets it, the server stores it as
given, and the server does not validate the format beyond the 64 byte length
check.

Ordering everywhere uses `updated_at`, descending. There is no sequence
number and no cursor, because there is no incremental sync: the client always
reads the full list.

## 8. Client side storage

The browser holds no copy of the vault beyond one in-memory snapshot. There
is no IndexedDB and no Dexie.

| Storage | Key | Contents |
|---|---|---|
| `localStorage` | `pv-theme` | `system`, `light` or `dark` |
| `localStorage` | `pv-locale` | `en` or `id` |
| `sessionStorage` | `pv-sw-reloaded-for` | the build id the tab already reloaded for |
| Module memory | none | the item snapshot in `src/hooks/useItems.ts` |

The snapshot is fetched when the first subscriber attaches, refreshed after
every mutation and on window focus, and cleared on logout. It is never
written to disk.

## 9. Migrations

`migrations/0001_init.sql` is the only migration. It was rewritten from
scratch when the app moved to the single password model, so the table names
and the columns are the ones above and nothing earlier survives.

```bash
npx wrangler d1 migrations apply personal-vault --remote   # production
npx wrangler d1 migrations apply personal-vault --local    # development
```
